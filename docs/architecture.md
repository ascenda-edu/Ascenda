# Ascenda — Architecture Overview

One-page orientation for developers new to the codebase. Operational detail (commands,
gotchas, env vars) lives in [CLAUDE.md](../CLAUDE.md) and [README.md](../README.md).

## Stack

Next.js 14 (App Router, `src/` root, `@/*` → `src/`) · TypeScript (strict) · Supabase
(Postgres + Auth + RLS) · TailwindCSS · Framer Motion. Deployed on Vercel (`main` →
production).

## Route map

| Area | Routes | Role |
|---|---|---|
| Student | `/dashboard`, `/university-search/*`, `/matches`, `/course/[id]`, `/shortlist`, `/applications(/tasks,/documents)`, `/profile`, `/scholarships`, `/toolbox/*`, `/inbox` | `student` |
| Counsellor | `/counsellor/*` (overview, inbox, students, universities, analytics, deadlines, outcomes, documents, applications) | `counsellor` (open to all — see Demo posture) |
| Parent | `/parent/*` (scoped family view via `guardian_links`) | linked guardian |
| Admin | `/admin` | `admin` only |

Auth guard pattern: server pages fetch `profiles.role` and `redirect()` on mismatch.

## Data layers (where the logic lives)

- `src/lib/supabase/` — client factories. `createServerSupabaseClient` (Server
  Components), `createRouteHandlerSupabaseClient` (API routes),
  `getBrowserSupabaseClient` via `useSupabase()` (Client Components),
  `service.ts` (server-only service-role client).
- `src/lib/counsellor/data.ts` + `types.ts` — counsellor data layer (real Supabase
  queries, cohort-scoped; see Demo posture).
- `src/lib/matching/`, `src/lib/scoring/`, `src/lib/tiering/` — programme matching
  engine, student scoring, and course tiering (the core domain logic; covered by the
  Jest suites in `__tests__/`).
- `src/lib/parent/` — parent-portal data layer scoped through `guardian_links`.
- `src/lib/api/guards.ts` — shared API-route helpers (`parseJsonBody`,
  `canActAsCounsellor`).
- `src/lib/validation/` — zod schemas for auth/profile forms.
- `src/lib/utils/dates.ts` — date-only strings must parse as LOCAL dates
  (`parseLocalDate`, `daysUntil`, `startOfToday`).

Components are grouped by domain under `src/components/`; page-private pieces live in
`_components/` folders next to their route.

## Demo posture (deliberate, reversible choices)

The app is currently demo-staged. These are intentional seams, not oversights:

1. **Open counsellor access** — migration
   `supabase/migrations/20260712130000_open_counsellor_access.sql` makes every
   signed-in user a counsellor (`can_act_as_counsellor()` → `auth.uid() is not null`).
   The migration header documents the exact one-line rollback for production.
2. **Seeded cohort filter** — counsellor queries are scoped to
   `+seed@ascenda.demo` emails (`DEMO_COHORT_EMAIL_SUFFIX` in
   `src/lib/counsellor/data.ts`). Remove when onboarding real students.
3. **Fixture-driven sections** — `src/lib/data/student-demo-data.ts` (demo student
   "Alex Morgan") backs the Toolbox area, some dashboard widgets, and some counsellor
   tabs with static data instead of Supabase queries. Its header comment lists
   consumers.
4. **Demo user discriminator** — `NEXT_PUBLIC_DEMO_EMAIL` (fallback in
   `src/lib/demo/demo-profile.ts`) marks the walkthrough demo account.
5. **Generated types lag** — `src/lib/types/database.ts` is regenerated manually
   (`npm run supabase:types`); tables added since the last run are typed manually in
   `src/lib/types/demo-tables.ts` and cast at the query seam.

## Database & migrations

- Canonical schema: `supabase/schema.sql` (RLS policies throughout). Seeds in
  `supabase/seed.sql`.
- Migrations: `supabase/migrations/*.sql`, written idempotently, applied **one at a
  time** via `npm run db:apply <file>` (`scripts/apply-sql.ts`). The remote migration
  history diverged from the folder, so `supabase db push` is unsafe — the script
  header explains why.
- Counsellor notifications are created by DB triggers (`SECURITY DEFINER`), not
  application code.
